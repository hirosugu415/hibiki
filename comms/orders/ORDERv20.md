# ORDER v20  (mode: innovation)

## 目的
7 点が 11 サイクル横ばいの壁を破るため、**通常訪問者（手紙を持たない人）の画面で見て分かる「新しい驚き」** を 3 案、`comms/IDEAS.md` に提案する。**実装はしない。**

## 現状（司令塔 v19: 7/10、コミット済み `bc41519`、ヘルス OK）
水面・石・砂州・長押しの泉・こだま・手紙（音つき再演・「響」で渡す）まで揃い、見た目は静かで一貫している。だが v15 以降、**初回訪問者が数十秒触った後の体験は変わっていない**。進歩が「受け手・共有」の見えにくい側に偏り、評価者の通常画面の印象は不変。すでに採用済み／試し済みなので再提案しない: 息の水面、長押しの泉、離しの大きな輪、浮かぶ石（押される）、砂州＋鐘、手紙（URL 楽譜）、ムード（凪・夜・暁）、こだま。

## やること（優先順）
1. **IDEAS.md に「Cycle 20 — 提案 (builder)」として案A・B・C の 3 案を追記**（既存内容は変更しない・追記のみ）。各案は次を必ず含める:
   - 概要・体験（初見の人が何をして何が起きるか）／なぜ他のアプリにないか
   - VISION の絶対のルールとの関係（UI を足すなら理由と、バー・ヒントとの共存。3 秒ルールを壊さない説明）
   - 使うブラウザ能力と、**デモモード（`?demo=1`）での評価方法**（`dataset` の値と、静止画で何が写れば合格か。probe の steps 例つき）
   - 1 サイクルの最小スコープ、実装規模（S/M/L）とリスク
   - 受け入れ条件: 「**手紙なし・初回訪問の通常画面の静止画で、前と違う何かが目に見える**」こと（受け手側・共有側だけに効く案は不可）
2. 末尾に「作業役の推し」を 1 案、理由つきで書く。
   - 受け入れ条件: 3 案が互いに領域の異なる案であること（下記の領域から最低 3 つ別々を選ぶ）。

## 発想してほしい領域と課題（この中から 3 つ別々に）
- **領域 P: 媒質**（墨・絹・砂・光る膜など）。cycle 4 から保留の課題。「ムード（色・音階）」とは別に、**触れた物質が変わると波の物理と音の質が同時に変わる**もの。最小スコープは 1 媒質。新しいバーのボタンを足す場合は既存 `.seg` の流儀（角丸・44px・線画アイコン・日本語 1〜2 文字）を厳守。
- **領域 Q: 入力の拡張**（マイクで水を揺らす・声の高さが波になる・傾き・音量）。ヘッドレスでは合成入力（`?demo=1`）で成立すること。許可 UI が 3 秒ルールを邪魔しない設計にすること。
- **領域 R: 作品が残る／持ち帰れる**（手紙とは別方式。光跡の一枚、水面の記憶、再訪時に前回の水が残っている等）。書き出しの検証が `dataset` と静止画でできること。
- **領域 S: 水面の世界を広げる**（水中・水底・季節・天候・生き物の気配など、触ると返ってくる新しい対象。石・砂州に続く第三の存在）。装飾でなく、**波と相互作用して音が鳴る**こと。
- **領域 T: 「次の一歩」の発見性**（手紙の「響」、長押し、石など、既にある深みに初見の人が説明文なしで気づく仕掛け）。ヒント文言を増やす案は不可。水・光・音の言語で導くこと。

## やらないこと
- `app/` のコード・`shots.json` の編集（**変更ゼロ**）。ビルド・実装の試作もしない（調査のために既存コードを読むのは可）。
- `comms/VISION.md`・`comms/STATE.json`・`harness/` の編集。
- 外部 API・バックエンド・外部通信・新規ライブラリを前提にした案。
- 上記「再提案しない」ものの焼き直し（拡張の形でも、それ自体が主眼なら不可）。

## 見た目・UX の要求（提案の評価基準）
- デスクトップ 1280×800 とスマホ 390×844 の両方で、Apple 製品のように静かで洗練された見た目が保てること。UI の追加は最小（できれば 0）。
- 初回タップで 3 秒以内に光の輪と音が返る既存体験を壊さない。
- 「機能が増えた」ではなく「触って気持ちよさ・驚きが増える」案を優先する。

## デモモード
- 各案について、`?demo=1`（カメラ・マイク・センサー無し）で司令塔が評価できる方法を具体的に書く。評価できない案は、設計ミスとして却下される。

## 作業役への注意
- 実装しないこと。**アプリを変更したら innovation の違反**（ハーネスが検知する可能性がある）。
- 3 案は「同じ案の大中小」ではなく、方向が違うものにする。1 案は、司令塔が過去に保留した方向（媒質・光跡の一枚など）でもよいが、却下理由（ボタン増・検証困難・明地と暗地のシェーダー衝突など）を解消する具体策を書く。
- REPORT には、提案した 3 案の一行要約と推しの理由、「アプリは変更していない」ことを書く。
- コミットに Claude を貢献者として入れない。`comms/VISION.md`・`comms/STATE.json` は触らない。
